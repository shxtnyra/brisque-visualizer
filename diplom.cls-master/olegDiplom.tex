\section{Клиент-серверная архитектура}
Клиент-серверная архитектура -- это распространенный подход в современной веб-разработке. При данном способе реализации есть два главных взаимодействующих компонента. Первый это клиент (frontend), он представляет собой ту часть, с которой взаимодействует пользователь. Второй это сервер (backend), который отвечает за логику веб-приложения: сохранение, получение, обработку и проверку данных. 

Для реализации их взаимодействия существует несколько подходов, но в рамках данной работы мы будем использовать SPA (Single Page Application). При этом подходе клиент загружает страницу только один раз, а затем все обновления содержимого страницы происходят динамически. 

В рамках SPA используется несколько видов обновления страницы (рендеринга). Мы будем использовать CSR (Client Side Rendering), или рендеринг на стороне клиента. При этом подходе на каждый новый запрос клиента сервер отправляет ответ в формате JSON с необходимой информацией, а клиент на ее основе рендерит страницу, которую увидит пользователь.

Для передачи данных между сервером и клиентом распространенным является архитектурный стиль REST (Representational State Transfer) [\ref{restrest}] для создания API (Application Programming Interface). При данном подходе сервер предоставляет набор эндпоинтов, каждый из которых имеет свой URI (Uniform Resource Identifier). Клиент для получения данных делает запрос с помощью стандартных HTTP методов (GET, POST и другие) на соответствующий эндпоинт, а в качестве ответа, в нашем случае, получает JSON.

REST API удобен для обычного взаимодействия с веб-приложением, но не подходит для взаимодействий в реальном времени -- например, таких как игровые сессии. В случае обновления состояния сервера клиент не получает его автоматически, для этого необходимо делать отдельный запрос. Это можно легко решить при помощи протокола WebSocket [\ref{websocket}]. Он предоставляет возможность создания постоянного двустороннего соединения между клиентом и сервером. Однако обычный WebSocket не очень удобен в использовании, так как он предоставляет лишь канал для обмена данными, всю обработку пакетов необходимо было бы реализовывать вручную. Поэтому удобнее будет использовать протокол STOMP (Simple Text Oriented Messaging Protocol) [\ref{stomp}] -- текстовый протокол для обмена данными, который является надстройкой над WebSocket. С его помощью легко реализовать взаимодействие между разными клиентами, используя шаблон Издатель-Подписчик. Сервер является брокером сообщений, предоставляя эндпоинты, на которые подписываются клиенты. Когда любой клиент отправляет данные на сервер в рамках соединения, то сервер отправляет обновление всем пользователям, которые подписаны на данный эндпоинт.

Он предоставляет набор инструментов для удобного написания RESTful сервисов [\ref{rest}], а также модули для обеспечения безопасности (Spring Security), а также работы с базами данных (Spring Data JPA [\ref{jpa}]). Также подключим библиотеку Lombok [\ref{lom}], которая позволяет автоматически генерировать шаблонный код для классов, указанных при помощи аннотаций. Будем использовать @Getter и @Setter для создания геттеров и сеттеров соответственно. @NoArgsConstructor, @AllArgsConstructor и @RequiredArgsConstructor для создания конструкторов классов по умолчанию, конструктора со всеми параметрами класса, а также конструктора только с необходимыми параметрами. @Builder для реализации паттерна билдер и @Data, которая включает в себя аннотации @Getter, @Setter и @RequiredArgsConstructor.

В качестве инструмента сборки используется Maven. 

Для реализации клиентской части был выбран фреймворк Vue.js. Он обладает архитектурой на основе компонентов, что позволяет повторно использовать элементы интерфейса. Благодаря системе реактивности, Vue.js автоматически отслеживает изменения данных и обновляет страницу без необходимости ручной перезагрузки.

\section{Безопасность данных}
Для осуществления процессов аутентификации и авторизации воспользуемся стандартом JWT (JSON Web Token) [\ref{jwt}]. При этом подходе после успешного ввода пользователем данных для входа, сервер отправляет в ответ JWT, который представляет собой структуру из трех составляющих: заголовка (header), полезной нагрузки (payload) и подписи (signature). В заголовке содержится информация об используемом алгоритме хеширования, в нашем случае это HMAC-SHA256, а также типе токена, у нас это JWT. В теле полезной нагрузки хранится информация самого токена, например, идентификатор пользователя, которому принадлежит токен, дата создания токена, дата истечения срока действия. К данным полям можно добавлять другие при необходимости. В подписи находится строка, получаемая путем хеширования на основе заголовка, полезной нагрузки, а также секретного ключа, который хранится на сервере. 

В ответ на успешный запрос аутентификации сервер отправляет два токена:

\begin{enumerate}[label=\arabic{enumi})]
	\item токен доступа (access token). Его срок действия сильно ограничен, обычно составляет менее часа. Необходим для доступа к защищенным ресурсам веб-приложения.
	
	\item токен обновления (refresh token). Его срок действия дольше, чем у токена доступа и может составлять от нескольких дней до нескольких недель. Используется для получения нового токена доступа без необходимости повторного ввода логина и пароля пользователем.
\end{enumerate}

\section{Алгоритмы проведения турниров}
Рассмотрим различные форматы проведения турниров. Широко распространенными системами являются олимпийская и швейцарская. Также рассмотрим алгоритмы начального распределения участников по сетке.

\subsubsection{Олимпийская система}
При олимпийской системе (single elimination) [\ref{olympic}] каждый участник играет до первого поражения. Если он проигрывает, то выбывает из турнира. Победителем турнира считается тот участник, который не проиграл ни одного матча. Количество раундов в данной системе вычисляется как $\lceil \log_2 N \rceil$, где $N$ -- число участников турнира.

\subsubsection{Швейцарская система}
В отличие от олимпийской системы, при швейцарской системе [\ref{swiss}] проводится ограниченное, заранее определенное число раундов и после поражения участники не выбывают из турнира. Для каждого участника ведется учет их побед, поражений и ничьих, которые переводятся в систему баллов. За победу дается один балл, за ничью половина балла, за поражение ноль (количество начисляемых баллов может отличаться для разных турниров).  При этом один участник не может играть против одного и того же соперника дважды. Все это учитывается при формировании пар для каждого раунда, следующего за первым. Победителем турнира считается тот участник, который обладает наибольшим числом очков.

\subsubsection{Начальное разбиение на пары}
Перед началом проведения турнира необходимо разбить участников на пары, которые составят матчи первого раунда. Для этого можно использовать несколько способов разбиения:

\begin{enumerate}
	\item \textbf{Случайное распределение.} Участники размещаются в сетке случайным образом, без учета их рейтинга.
	
	\item \textbf{Распределение по рейтингу.} Участники сортируются по возрастанию их рейтинга. Затем каждые два участника образуют пару. При таком подходе каждый игрок получает максимально близкого по уровню игры соперника.
	
	\item \textbf{Прямое распределение.} Участники сортируются по убыванию их рейтинга и затем делятся на две равные группы. Пары составляются так, что первый игрок из первой группы будет в паре с первым игроком из второй группы, второй со вторым и аналогично для всех игроков. 
	
	\item \textbf{Распределение змейкой.} Участники сортируются по убыванию рейтинга и затем делятся на две равные группы. Пары составляются так, что первый игрок из первой группы будет в паре с последним игроком из второй группы, второй с предпоследним и аналогично для всех игроков.
	
	\item \textbf{Распределение по рейтингу со случайным блужданием.} Комбинированный подход, при котором сетка строится на основе рейтинга, но с элементами случайности. Участники сортируются по возрастанию рейтинга. Затем берется случайный игрок, а пара для него выбирается случайно из окрестности, радиус которой вычисляется по формуле: $R = \frac{\sigma \cdot M}{10}$, где $M$ -- число участников без пары, $\sigma$ -- коэффициент для управления шириной области. Так повторяется до тех пор, пока все игроки не получат пару.
\end{enumerate}

\section{Разработка серверной части}
Как упоминалось ранее, серверная часть приложения реализована на языке Java с использованием фреймворка Spring Boot. Рассмотрим подробнее детали реализации.

\subsection{Архитектура}
Для написания серверной части веб-приложения была выбрана слоистая архитектура. Этот подход широко распространен при использовании фреймворка Spring. При данном подходе приложение содержит несколько уровней, каждый из которых отвечает за свою логику. Стандартным подходом является использование следующих слоев:

\begin{enumerate}
	\item \textbf{Контроллер}. Набор REST-контроллеров, которые обрабатывают HTTP-запросы. Сюда также входят контроллеры WebSocket.
	\item \textbf{Сервис}. Слой Spring-сервисов, реализующий бизнес-логику, следует за контроллерами.
	\item \textbf{Репозиторий}. Слой доступа к базе данных, реализован с помощью Spring Data JPA.
\end{enumerate}

Для передачи данных от сервера к клиенту воспользуемся паттерном DTO (Data Transfer Object) [\ref{dto}]. Он представляет из себя класс-контейнер для данных. Его использование позволит передавать только необходимые данные, вместо полных сущностей. 

\subsection{Проектирование базы данных}
В качестве основных компонентов для работы с базой данных в JPA выступают сущности (Entity). Это специальные классы, через которые указываются желаемые поля в создаваемой таблице. Этот же класс служит шаблоном для создания объектов при получении данных из базы данных. В рамках работы были реализованы следующие сущности:

\begin{itemize}
	\item \textbf{UserEntity}. Хранит информацию о пользователях: идентификатор, имя, пароль, почту, роль, рейтинг, дату регистрации, ссылку на аватар.
	\item \textbf{RefreshTokenEntity}. Хранит информацию о токенах обновления для JWT-аутентификации: идентификатор, токен, пользователя, которому принадлежит токен и дату истечения срока действия токена.
	\item \textbf{TournamentEntity}. Хранит информацию о турнирах.
	\item \textbf{TableEntity}. Хранит информацию о турнирной таблице: идентификатор, число участников, текущий раунд, список раундов, список статистики швейцарской системы и турнир, к которому относится таблица.
	\item \textbf{SwissTableEntity}. Хранит статистику игроков в швейцарской системе: идентификатор, таблицу, к которой относится, число побед, поражений, ничьих, общий счет и число сыгранных матчей.
	\item \textbf{RoundEntity}. Хранит информацию о раундах: идентификатор, номер раунда, список матчей данного раунда и турнирную таблицу, к которой относится раунд.
	\item \textbf{MatchEntity}. Хранит информацию о матчах: идентификатор, данные об участниках матча, о победителе, о следующем матче по таблице (куда перейдет победитель, необходимо для олимпийской системы), закончен ли матч, закончился ли матч ничьей и раунд, в котором проводится матч.
\end{itemize}

Связи между сущностями реализованы следующим образом:
\begin{itemize}
	\item \textbf{UserEntity (1) $\rightarrow$ TournamentEntity (N)}: один пользователь может быть организатором нескольких турниров, связь One-to-Many.
	
	\item \textbf{UserEntity (1) $\rightarrow$ RefreshTokenEntity (N)}: один пользователь может иметь несколько refresh-токенов.
	
	\item \textbf{UserEntity (1) $\rightarrow$ SwissTableEntity (N)}: у одного пользователя может быть несколько записей статистики (для разных турниров).
	
	\item \textbf{TableEntity (1) $\rightarrow$ SwissTableEntity (N)}: одна турнирная таблица содержит множество записей статистики игроков для швейцарской системы (по одной на каждого участника).
	
	\item \textbf{TableEntity (1) $\leftrightarrow$ TournamentEntity (1)}: один турнир имеет ровно одну турнирную таблицу, связь One-to-One.
	
	\item \textbf{TableEntity (1) $\rightarrow$ RoundEntity (N)}: одна турнирная таблица содержит множество раундов.
	
	\item \textbf{RoundEntity (1) $\rightarrow$ MatchEntity (N)}: один раунд содержит множество матчей.
	
	\item \textbf{TournamentEntity (N) $\leftrightarrow$ UserEntity (N)}: один турнир может содержать множество участников, один пользователь может участвовать во множестве турниров. Связь Many-to-Many, реализована через связующую таблицу tournament\_participants.
\end{itemize}

Рассмотрим более подробно реализацию сущности TournamentEntity. 
\begin{lstlisting}[language=Java, showstringspaces=false]
@Entity
@Table(name = "tournaments")
@Getter
@Setter
@Builder
@NoArgsConstructor
@AllArgsConstructor
public class TournamentEntity {
	@Id
	@GeneratedValue(strategy = GenerationType.IDENTITY)
	private Long id;
	
	@Column(nullable = false, updatable = false)
	private String name;
	
	@Enumerated(value = EnumType.STRING)
	@Column(nullable = false, updatable = false)
	private GameType gameType;
	
	@Enumerated(value = EnumType.STRING)
	@Column(nullable = false)
	private TournamentSystem system;
	
	@Column(name = "is_over", nullable = false, 
	columnDefinition = "boolean default false")
	private boolean isOver = false;
	
	@Column(name = "start_date", nullable = false)
	private LocalDateTime startDate;
	
	@Column(name = "finish_date")
	private LocalDateTime finishDate;
	
	@ManyToOne(fetch = FetchType.LAZY)
	@JoinColumn(name = "user_id")
	private UserEntity organizer;
	
	@ManyToMany(fetch = FetchType.LAZY)
	@JoinTable(name = "tournament_participants",
	joinColumns = @JoinColumn(name = "tournament_id"),
	inverseJoinColumns = @JoinColumn(name = "user_id")
	)
	private List<UserEntity> participants = new ArrayList<>();
}
\end{lstlisting}
При помощи аннотации @Entity мы помечаем, что этот класс является JPA-сущностью. В @Table указываем название соответствующей классу таблицы в базе данных. Используем аннотации @Getter, @Setter, @Builder, @NoArgsConstructor, \\ @AllArgsConstructor из lombok для автоматического создания соответствующих методов для нашего класса.

Рассмотрим поля этого класса. 
\begin{itemize}
	\item \textbf{id}. Поле id имеет аннотации @Id и @GeneratedValue, что указывает, что именно это поле будет являться первичным ключом или же идентификатором сущности, а также будет генерироваться автоматически при вставке сущности в базу данных.
	\item \textbf{name}. Поле name хранит название турнира и отмечено аннотацией @Column, в которой можно указать название столбца в БД, а также задать параметры: в нашем случае поле обязательно должно быть заполнено, то есть не может иметь значение null (nullable = false), а также его запрещено обновлять (updatable = false).
	\item \textbf{gameType}. Поле gameType имеет тип GameType -- класс перечисление (Enum), поэтому его нужно обозначить аннотацией @Enumerated, используя value = EnumType.STRING мы указываем, что храниться значения в базе данных должны в виде строк.
	\item \textbf{system}. Хранит тип турнирной системы (олимпийская или швейцарская).  Аннотируется аналогично полю gameType.
	\item \textbf{isOver}. Хранит флаг, показывающий закончен ли турнир. Параметр \\ columnDefinition = \char`\"boolean default false\char`\"~указывает значение поля по умолчанию -- false.
	\item \textbf{startDate}. Хранит дату начала турнира.
	\item \textbf{finishDate}. Хранит дату окончания турнира.
	\item \textbf{organizer}. Хранит пользователя-организатора турнира. Является внешним ключом на таблицу users. Аннотация @ManyToOne указывает, что владельцем связи будет сущность TournamentEntity. Параметр fetch = FetchType.LAZY указывает на ленивую загрузку, то есть загрузка данного поля будет происходить не при любом обращении к сущности TournamentEntity, а только при явном получении доступа к полю organizer. Аннотация @JoinColumn(name = \char`\"user\_id\char`\") задает имя внешнего ключа в сущности TournamentEntity. 
	\item \textbf{participants}. Хранит список участников турнира, реализуя связь многие-ко-многим (@ManyToMany). Для реализации связи укажем необходимые параметры в аннотации @JoinTable. Укажем название связующей таблицы name = \char`\"tournament\_participants\char`\", параметр joinColumns указывает на поле в связующей таблице, которое будет ссылаться на текущую сущность, то есть \char`\"tournament\_id\char`\". Параметр inverseJoinColumn определяет поле в связующей таблице для связи другой сущности (UserEntity), то есть укажем \char`\"user\_id\char`\".
\end{itemize}

\subsection{Реализация контроллеров}
Рассмотрим один из основных контроллеров -- TableController, который отвечает за работу с турнирными таблицами. В качестве базового пути к контроллеру выберем \char`\"/v1/tournaments\char`\". Для работы нам потребуется реализовать четыре метода: \begin{itemize}
	\item \textbf{findTableByTournament}. Метод используется для получения полной информации о турнирной таблице турнира.
	\item \textbf{createTable}. Используется для создания турнирной таблицы: создания раундов и начального распределения участников по матчам.
	\item \textbf{replaceTableByTournamentId}. Полная замена таблицы, все предыдущие данные о раундах и матчах будут удалены.
	\item \textbf{updateMatchByTournamentId}. Обновляет результаты выбранного матча.
\end{itemize}

Для первых трех методов будем использовать один путь -- \char`\"/{id}/table\char`\", где id -- идентификатор турнира.

Для получения таблицы будем использовать GetMapping. Для создания таблицы будем использовать PostMapping, в качестве тела запроса метод ожидает TableCreateDTO с полями participantsCount -- число участников и type, который отвечает за способ начального распределения участников на пары. В поле type ожидается одно из возможных значений: TABLE\_RATING, TABLE\_RANDOM, TABLE\_SNAKE, TABLE\_PARALLEL, TABLE\_RANDOM\_WALK. Для замены таблицы будем использовать PutMapping, так как это полная замена ресурса. В качестве тела запроса метод ожидает TableCreateDTO.

Для обновления результатов матча будем использовать PatchMapping по пути "/{id}/table/matches/{match\_id}\char`\", так как это частичная замена ресурса. Ожидаемым телом запроса является TableUpdateDTO, содержащий winnerId -- идентификатор победителя матча и isDraw -- флаг, показывающий закончился ли матч ничьей. Итоговый вид контроллера можно увидеть в приложении~\ref{contTable:1}.

\subsection{WebSocket}
Для работы WebSocket создадим класс конфигурации WebSocketConfig, реализующий интерфейс WebSocketMessageBrokerConfigurer. Для реализации интерфейса необходимо переопределить два метода: configureMessageBroker и \\ registerStompEndpoints. Рассмотрим их реализацию.
\begin{lstlisting}[language=Java]
@Override
public void configureMessageBroker(MessageBrokerRegistry config) {
	config.enableSimpleBroker("/topic", "/queue");
	
	config.setApplicationDestinationPrefixes("/v1");
	
	config.setUserDestinationPrefix("/user");
}
\end{lstlisting}
Данный метод необходим для конфигурации брокера сообщений, который управляет маршрутизацией сообщений между клиентами и сервером:

\begin{itemize}
	\item \textbf{enableSimpleBroker(\char`\"/topic\char`\", \char`\"/queue\char`\")}. Включает встроенный простой брокер сообщений. Префикс /topic используется для рассылок всем подписчикам (например, обновление состояния игрового поля), а /queue -- для сообщений конкретному пользователю.
	
	\item \textbf{setApplicationDestinationPrefixes(\char`\"/v1\char`\")}. Задает префикс для адресов назначения, которые обрабатываются методами контроллеров с аннотацией @MessageMapping.
	
	\item \textbf{setUserDestinationPrefix(\char`\"/user\char`\")}. Задает префикс для адресов, по которым будут отправляться индивидуальные уведомления пользователям.
\end{itemize}

\begin{lstlisting}[language=Java]
@Override
public void registerStompEndpoints(StompEndpointRegistry registry) {
	registry.addEndpoint("/v1/checkers", "/v1/chess")
	.setAllowedOrigins("http://localhost:5173")
	.withSockJS();
}
\end{lstlisting}
Данный метод необходим для регистрации WebSocket-эндпоинтов, по которым клиенты могут устанавливать соединение:

\begin{itemize}
	\item \textbf{addEndpoint(\char`\"/v1/checkers\char`\", \char`\"/v1/chess\char`\")}. Добавляет два WebSocket-эндпоинта для различных игр. Клиенты подключаются к этим адресам, чтобы установить WebSocket-соединение с сервером.
	
	\item \textbf{setAllowedOrigins(\char`\"http://localhost:5173\char`\")}. Указывает разрешенные источники для CORS.
	
	\item \textbf{withSockJS()}. Включает поддержку SockJS -- библиотеки, которая эмулирует WebSocket в браузерах, не поддерживающих этот протокол, автоматически выбирая наиболее подходящий способ замены.
\end{itemize}

Рассмотрим пример реализации контроллера WebSocket для игры в шахматы -- ChessController. В качестве базового пути для обращения к контроллеру служит \char`\"/chess\char`\". Для реализации игры нам потребуется создать четыре метода: createLobby, joinLobby, makeMove и getGameState. Рассмотрим подробнее каждый из методов.

Метод createLobby отвечает за создание игровой комнаты, привязанной к существующему в системе матчу. После создания комнаты сервер отправляет обновленное состояние игры всем клиентам, подписанным на /topic/chess/\{matchId\}.

\subsection{Реализация логики шашек и шахмат}
В рамках разработанного приложения реализована поддержка двух настольных игр: шахмат и шашек. 

\subsubsection{Хранение состояния игры}
Состояние игровой доски шашек представлено в виде двумерного массива строк (матрицы 8 на 8), где каждая ячейка содержит информацию о цвете фигуры, позиция на доске соответствует индексации в матрице. Для шахмат создан абстрактный класс Piece, от которого наследуются классы для каждого из типа фигур. Доска хранится в двумерном массиве типа Piece. Для обеих игр также хранится информация о текущем ходе, идентификаторы игроков за белые и черные фигуры, цвет выигравшей стороны. 

\subsubsection{Совершение ходов}
Одним из главных моментов реализации является осуществление хода, которая включает проверку корректности. Алгоритм осуществления хода в шашках состоит из следующих этапов:

\begin{enumerate}
	\item Проверка, что игра не окончена и ход делает тот игрок, чья сейчас очередь.
	\item Если обязателен захват после предыдущего взятия (захват нескольких шашек за раз), проверка, что ходит та же фигура, которая только что совершила захват.
	\item Проверка, что ход совершает корректная фигура.
	\item Определение, есть ли у игрока доступные захваты и проверка хода с учетом обязательности захвата.
	\item Выполнение перемещения фигуры с начальной клетки на конечную и удаление всех захваченных фигур, если они есть.
	\item Проверка, закончилась ли игра победой текущего игрока, то есть у противника не осталось фигур.
	\item Превращение фигуры в дамку при достижении последней горизонтали.
	\item Если был совершен захват и фигура может захватить дальше, то устанавливаем флаг обязательного продолжения захвата.
	\item Иначе -- сброс цепочки захвата и передача хода противнику.
\end{enumerate}

Алгоритм хода в шахматах:
\begin{enumerate}
	\item Проверка, что игра не окончена.
	\item Проверка, что на начальной клетке находится фигура текущего игрока.
	\item Получение списка возможных ходов для этой фигуры и проверка, что целевая клетка хода входит в этот список.
	\item Обработка особых случаев перед выполнением хода:
	\begin{enumerate}
		\item Проверяем является ли ход взятием на проходе и сохраняем информацию о взятой пешке.
		\item Определяем является ли ход рокировкой. Если рокировка была совершена, то сохраняем информацию об участвовавших фигурах.
		\item Проверяем является ли ход превращением пешки в ферзя.
	\end{enumerate}
	\item Выполнение перемещения фигуры.
	\item Проверка, не остался ли свой король под шахом после выполнения хода. Если остался, то делаем откат хода.
	\item Передача хода противнику.
	\item Проверка окончания игры. Если противник в мате, то устанавливаем победителя. Если пат, сохраняем ничью.
\end{enumerate}
Для получения списка возможных ходов в классах каждой из фигур были реализованы методы, возвращающие список возможных позиций для текущего хода.
До осуществления хода создается объект, хранящий всю необходимую информацию для возвращения исходного состояния поля: фигура, которая совершала ход, взятая фигура, информация о рокировке, взятии на проходе, превращении пешки в ферзя.

\section{Реализация логики турниров}
Разберем основные детали реализации алгоритмов для проведения турниров.

\subsection{Распределение на пары}
Как упоминалось ранее, для начального разбиения на пары было выбрано несколько алгоритмов. Разберем методы, которые их реализуют. Каждый из методов на вход получает список участников и список для записи составленных пар.

Для случайного распределения воспользуемся стандартным классом Collections. Он предоставляет метод shuffle, который возвращает случайным образом перемешанную коллекцию. После этого будем брать каждые 2 участника из списка и записывать их в пару.

Для распределения по рейтингу отсортируем список участников по возрастанию рейтинга и затем аналогично предыдущему методу запишем участников в матч.

Для прямого распределения отсортируем список участников по убыванию рейтинга. Для составления пар будем брать sortedPlayers.get(i) и sortedPlayers.get(i + half), где half -- число участников, разделенное на 2.

Для распределения змейкой отсортируем список участников по убыванию рейтинга. Выделим с помощью метода sublist вторую половину списка в отдельный список. Затем развернем его с помощью метода reverse. Для составления пар будем брать sortedPlayers.get(i) и reversedPlayers.get(i).

Для распределения по рейтингу со случайным блужданием отсортируем список участников по возрастанию рейтинга. Затем создадим список свободных игроков. Пока в списке свободных остается хотя бы 2 игрока, будем делать следующее: выберем случайный индекс первого игрока. Определим область поиска для второго игрока, чем больше значение $\sigma$, тем шире разброс относительно первого игрока. Рассчитаем диапазон индексов (от start до end) с учетом минимального смещения MIN\_OFFSET. Если диапазон оказался слишком узким, то расширим его на один элемент влево или вправо. Второго игрока выберем случайно из списка участников, входящих в этот диапазон, исключая первого. Создадим пару из двух игроков и удалим обоих из списка свободных.

Полный код методов составления пар представлен в приложении \ref{pairs:1}.

\subsection{Олимпийская система}
Так как в олимпийской системе можно до начала турнира определить необходимое для проведения число раундов и матчей, то при инициализации турнира сразу создадим необходимые раунды и матчи. Ограничим возможные варианты числа участников $N$ следующими: 2, 4, 8, 16, 32, 64. Тогда количество раундов вычисляется по формуле $\log_2 N$. Создадим пустые раунды, сохраняя их в базу данных, и привяжем к турнирной таблице. Затем для каждого раунда сгенерируем матчи на основе списка участников и выбранного типа распределения. После создания всех матчей свяжем их между собой: для каждых двух матчей текущего раунда укажем следующий матч в следующем раунде, это необходимо для удобного перевода победителей в следующие матчи.

Также рассмотрим метод для обновления результатов матчей. В случае, если матч окончился ничьей, то он не считается завершенным и требуется переигровка между теми же игроками до первой победы. Иначе, отмечаем матч завершенным, устанавливаем победителя и переводим его в следующий матч. Также проверяем, не завершился ли текущий раунд и если да, то переводим турнир в следующий раунд (если текущий раунд это не финал). Дополнительно, начисляем победителю рейтинг за победу в виде фиксированной добавки $+5$ в обычном матче и дополнительные $+15$ за победу в турнире. То есть, чемпион турнира получит $5k + 15$ рейтинга, где $k$ -- количество выигранных матчей. Остальные участники получают рейтинг только за выигранные ими матчи.

Полный код методов создания турнирной сетки и обновления результатов матча представлен в приложении \ref{olymp:1}.

\subsection{Швейцарская система}
Как упоминалось ранее, в отличие от олимпийской системы, в швейцарской системе пары для матчей подбираются на основе результатов уже сыгранных матчей. Разберем подробнее реализованный алгоритм:
\begin{enumerate}
	\item Отсортировать участников по количеству набранных очков (по убыванию).
	\item Для текущего участника $P$:
	\begin{enumerate}
		\item Взять список свободных участников-кандидатов.
		\item Для каждого кандидата $C$ проверить, играл ли он против $P$. Если да -- пропускаем и берем нового кандидата. 
		\item Если не играли, то вычисляем разницу очков:
	\[
	score(P, C) = |points(P) - points(C)| + ratingDifference(P, C),
	\]
	где $ratingDifference$ определяется следующим образом:
	\[
	ratingDifference = 
	\begin{cases}
		+1, & \text{если } |rating(P) - rating(C)| > 200 \\
		-0.5, & \text{если } |rating(P) - rating(C)| < 50 \\
		0, & \text{иначе}
	\end{cases}
	\]
		\item Выбрать кандидата с наименьшим значением $score$.
	\end{enumerate}
	\item Если список кандидатов пуст, выбрать ближайшего по очкам из всех свободных участников, даже если они уже играли друг против друга.
\end{enumerate}

Полный код метода для подбора соперника в швейцарской системе представлен в приложении \ref{swiss:1}.

\section{Разработка клиентской части}
Как упоминалось ранее, для разработки клиентской части используется Vue.js. Рассмотрим подробнее некоторые детали реализации.

Корневой компонент приложения App.vue задаёт общий каркас интерфейса, а именно верхнюю навигационную панель и область <router-view />, в которую Vue Router подставляет активное представление. Панель навигации адаптируется к состоянию авторизации: для аутентифицированного пользователя отображаются ссылки на профиль и кнопка выхода, для гостя -- вход и регистрация.

\subsubsection{Маршрутизация}
Маршрутизация приложения реализована с помощью Vue Router. Рассмотрим главные пути и компоненты, которые привязаны к ним.

\begin{enumerate}
	\item \texttt{/} -- \textbf{Компонент:} \texttt{MainView}. Главная страница приложения.
	
	\item \texttt{/register} -- \textbf{Компонент:} \texttt{RegisterComponent}. Страница для регистрации пользователя.
	
	\item \texttt{/profile} -- \textbf{Компонент:} \texttt{ProfileView}. Страница просмотра личного профиля. Требует авторизации.
	
	\item \texttt{/tournaments/:id} -- \textbf{Компонент:} \texttt{TournamentView}. Страница детальной информации о конкретном турнире.
	
	\item \texttt{/tournaments/:id/bracket} -- \textbf{Компонент:} \texttt{TournamentTableView}. Страница отображающая турнирную сетку.
	
	\item \texttt{/game/checkers/:id} -- \textbf{Компонент:} \texttt{CheckersView}. Страница для игры в шашки. Требует авторизации.
	
	\item \texttt{/game/chess/:id} -- \textbf{Компонент:} \texttt{ChessView}. Страница для игры в шахматы. Требует авторизации.
\end{enumerate}

\chapternonum{Заключение}

В результате работы было разработано веб-приложение для организации и проведения турниров по настольным играм, включающее серверную и клиентскую части. 

Были реализованы различные алгоритмы проведения турниров: олимпийская система и швейцарская система. Реализованы методы начального распределения участников по парам с учетом рейтинга и заданного типа распрелеления, а для швейцарской системы -- алгоритм
подбора соперников с учетом текущих результатов и рейтинга участников.

Также была реализована игровая логика шашек и шахмат с возможностью игры двух игроков в рамках турнира. Для каждой игры реализована проверка правил ходов, фиксация промежуточных состояний доски, определение победителя и автоматическая передача результата в турнирную логику.

Для разработки приложения использовались: язык программирования Java (фреймворк Spring Boot), Vue.js (для клиентской части), СУБД PostgreSQL.
